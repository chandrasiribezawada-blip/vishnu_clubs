# VishnuConnect API

This directory contains the persistent VishnuConnect API: PostgreSQL-backed student
accounts and sessions, clubs, follows, membership requests, coordinator decisions,
events, registrations, QR passes, attendance, notifications, audit records, and
administrator coordinator assignments.

## Local setup

1. Install Python 3.12 or newer and PostgreSQL 15 or newer.
2. Create a database and user for local development.
3. Copy `.env.example` to `.env`, then configure `DATABASE_URL` and a random
   `JWT_SECRET_KEY`. Never use the example values outside local development.
4. From this directory, install dependencies and run migrations:

   ```powershell
   py -m venv .venv
   .\.venv\Scripts\Activate.ps1
   pip install -r requirements.txt
   alembic upgrade head
   python -m app.scripts.seed_clubs
   uvicorn app.main:app --reload
   ```

5. Open `http://127.0.0.1:8000/docs` for the OpenAPI reference and
   `http://127.0.0.1:8000/health` for the process health check.

`docker compose up --build` from the Flutter project root starts the local
PostgreSQL database and API. Set a strong `JWT_SECRET_KEY` in the environment
before starting the API container. Migrations run before the API starts, followed
by the idempotent seed for the 23 official club names and their existing categories.
The same seed command can be safely rerun after startup.

## Initial administrator

After migrations, create the first administrator through the one-time bootstrap
command; it prompts for the password instead of accepting it in shell history:

```powershell
python -m app.scripts.bootstrap_admin --email admin@example.edu --name "Club Admin"
```

The command refuses to create a second bootstrap administrator. Coordinators are
assigned by an authenticated administrator through
`POST /api/v1/admin/clubs/{club_id}/coordinators`.

## Implemented API

- `POST /api/v1/auth/register`, `/login`, `/refresh`, `/logout`; `GET /auth/me`
- `GET /api/v1/clubs` (23 seeded clubs), `GET /clubs/{id}`,
  `POST|DELETE /clubs/{id}/follow`,
  and `GET /me/followed-clubs`
- Student requests: `POST /clubs/{id}/join-requests`,
  `GET /me/join-requests`, and `GET /me/memberships`
- Coordinator queue: `GET /me/coordinator-clubs` and
  `GET /clubs/{id}/join-requests`; the latter is limited to pending requests
  for a currently assigned club
- Coordinator dashboard: `GET /coordinator/dashboard` returns summary metrics
  only for active club assignments belonging to the authenticated
  `CLUB_MEMBER_COORDINATOR`
- Coordinator decisions: `POST /join-requests/{id}/approve` or `/reject`;
  decisions are single-use, and approval plus active membership, notification,
  and audit record are committed atomically
- Admin coordinator assignment/revocation
- Admin-only `GET /admin/dashboard`, `/admin/users`, and `/admin/coordinators`
  for the in-app coordinator assignment workspace
- Authenticated `GET /me/notifications` and
  `PATCH /me/notifications/{id}/read`; notifications are private to their
  recipient and are generated by membership and attendance workflows

Registration always creates a `STUDENT` and rejects client-supplied role fields.
All three account types use the same login endpoint; the returned role comes from
the database and controls the Flutter workspace. An administrator assigns an
existing student account to a club to grant coordinator access; the first admin is
created only through the one-time bootstrap command above. Coordinator access is
checked against the current, unrevoked database assignment on every protected
membership operation. Notifications and audit records for membership actions are
committed in the same transaction as the domain change. PostgreSQL
constraints enforce a valid initial pending status, one pending request per
student/club, one decision per request, and no duplicate active membership.

Events are coordinator-managed and scoped to currently assigned clubs. Students can
register and cancel before the event starts. A pass is issued only for an active
registration; its random token is returned once and only its SHA-256 digest is stored.
Passes expire at the event end, are revoked when the registration/event is cancelled,
and can be consumed only once by a coordinator assigned to that event's club. The
attendance record and in-app notification are committed transactionally. The student
pass endpoint sends `Cache-Control: no-store, private`; clients should not persist or
log the QR payload.

Published events can be listed with `GET /events?include_past=true`; the default
continues to return upcoming published events. Assigned coordinators can retrieve
event participants with per-person attendance status and an attendance summary. The
Flutter client provides event search/range/category filters, system-share-sheet event
sharing, and Google Maps directions. These external-app actions require a device or
browser with a compatible handler.

Announcements, push/device notifications, media uploads, editable club metadata,
and richer profile administration are not implemented. The current notification
inbox is persistent in-app state only; it does not send push notifications.

## Tests

```powershell
pytest
```

Tests use an isolated in-memory SQLite database. Production/local runtime uses
PostgreSQL; startup never creates tables automatically. Schema changes are made
through Alembic migrations. SQLite tests verify the API and persistence paths but do
not verify PostgreSQL row-lock concurrency behavior.
